# v0.9.2a1 local security-review guide

This is a local hardening candidate. No push, publication, new recovery default,
production approval or independent audit is implied. The supported boundary is
still the registered broker tools and adapter-returned final text, with a trusted
Python process, operator, model transport/history and OS account.

## Outcome contract

Authorization status (`allowed`, `blocked`, `sent_for_approval`) and execution
certainty remain separate. No new wire enum is required:

| execution | Meaning | Continuation |
| --- | --- | --- |
| not_run | Dispatch did not start: denied, pending or capacity/state rejection | Never equate with task completion |
| failed | Trusted executor establishes failure before a protected write/network effect or tool-data release | A new permitted proposal may be possible; no success claim |
| succeeded | The supported tool returned normally | Verify actual business receipts/state separately |
| unknown | Dispatch may have had an effect, or post-dispatch observation/completion audit failed | Output withheld; session and supported adapter run halt for operator review |

For example, a receiver can accept a POST and then disconnect, send HTTP 500 or
return invalid text. The broker cannot establish absence of effects from those
responses. An observation-audit error after a received POST is likewise uncertainty.
A missing readable file or refused exclusive create can be a known pre-effect
failure. Validation/policy rejection is not_run. An audit failure before dispatch
raises before any tool call and halts that session; it does not fabricate a durable
event ID or return a misleading successful result.

`AgentExecutionUncertain` is a fatal adapter exception, not a model retry prompt.
Subsequent submissions/final output in the same halted session cannot proceed.
This does not guarantee exactly-once transactions or prevent a trusted caller from
deliberately starting another authorized session. Do not implement automatic
replacement-run retries. Reconcile using actual simulator/service/filesystem state.

## Approval lifecycle

The 1,000-entry queue cap is checked before the sent_for_approval record. Overflow
is blocked/not_run with no approval ID; it is not counted as accepted pending work.
Expiration and retirement invalidate grants before attempting terminal audits.
Audit unavailability can therefore leave an incomplete terminal record but cannot
revive a grant. Approval resolution remains operator-only, action/session/policy
bound, expiring and single-use, and rechecks current policy and confidentiality.
Pending grants are memory-only and cannot survive broker restart.

## Durable count-release reservations

New state databases have `release_budget_meta_v1` and `release_budgets_v1` tables
in the same operator-owned SQLite database as audit events. Only a genuinely new
AuditStore initializes the format. First use binds one canonical workspace identity.
Scope keys hash that identity, case-folded source components and exact destination;
source contents, request bodies and credentials are never stored in the ledger.
Policy names/digests/rule IDs and source-content changes do not renew a budget.
Changing max_releases is an explicit operator policy decision, not an implicit reset.

Reservations use a bounded SQLite write-lock wait, BEGIN IMMEDIATE and FULL
synchronization. An attempt commits **before** pre-effect audit/source/transport,
so a subsequent audit failure, invalid projection or process crash consumes it.
Exhaustion or missing/corrupt/unreadable/locked state denies before source content
access or HTTP effects. Audit-row retention never removes reservation tables.
If recording the denial also fails, no effect occurs and an exception is raised.
The audit writer retains its own bounded connection timeout.

Back up the complete SQLite database consistently, not just exported audit events.
Restoring an older snapshot, deleting state or modifying it as the trusted OS owner
can invalidate accounting. No protection against such an administrator, arbitrary
filesystem rollback or physical power-loss guarantees is claimed. Tests exercise
process crashes, not every storage device/power-failure condition.

### Migration restriction

Existing databases without this format are **not auto-migrated**, even when audit
rows contain no release evidence: retention may have deleted them. Count release
fails closed with release_state until an operator reviews the old grants and state.
Ordinary non-release operations remain available under their existing permissions.
Do not delete an old database or silently start a new one to resume an old grant.
No general historical-budget migration/reset tool is provided in this candidate.
Moving a bound database to a different workspace also requires explicit review.
Mixed old/new writer versions against one state database are unsupported.

The budget limits approved cardinality releases, not arbitrary semantic disclosure,
timing channels or all repeated-query leakage. Existing fixed projector/read/send
permissions, failure consumption and sticky confidentiality still apply.

## Session retirement

Call `broker.retire_session(session_id)` only from trusted operator/application code.
It removes the session ID and cancels all its pending approvals before audit, so
an error does not leave the old authority reusable. It never refunds release
reservations or exposes a model-controlled clean-session switch. Agent API
credentials keep their original idempotent session binding; there is no agent
retirement/reset route. Retiring that API-bound session does not give the credential
a new session automatically.

Completed fresh-context SDK calls can opt into `retire_on_exit=True`; default false
preserves callers that need pending approvals. The option cancels those approvals
even on failure, so select it deliberately. It does not erase model/provider memory:
never resume classified history under a new session. The public factory creates
fresh run history and does not accept caller-provided message history. It cannot
constrain arbitrary custom callbacks or another agent.

## Strict profile and legacy compatibility

`Policy(profile="strict", ...)` is opt-in. Legacy remains the default and its
profile/acknowledgment defaults are omitted from serialization, preserving old
policy digests and partial-key behavior. `Policy.diagnostics()` returns fixed
configuration warnings; it does not inspect personal files, discover secrets or
make authorization decisions using model text.

Strict mode requires nonempty sensitive_roots, exact explicit outgoing POST fields,
and review of read scopes overlapping classification. Such a read requires the
operator's explicit `sensitive_reads_acknowledged=True`; it still taints the session
and never declassifies output. Arbitrary POST body permissions and approval-only
POST rules without a closed schema are rejected. File creation still uses its
scoped permission/approval and is not a general structured-output validator.

The strict closed-message profile explicitly rejects legacy count-release grants;
their current broad send permission is not a compatible closed message schema.
Use the separately reviewed legacy release mechanism with its exact operator grant
when needed. This incompatibility is diagnosed, not silently bypassed or weakened.

```python
from zyntrava.policy import strict_status_policy

policy = strict_status_policy("http://127.0.0.1:8766/collect")
```

This permits only public/status.txt and exactly `{"status":"ready"}` at that exact
numeric-loopback endpoint. An extra recipient, amount or other field is rejected.
No mode relies on credential regexes as complete DLP. Suspicious instruction text
continues to be an observation; permission enforcement is independent of that heuristic.

## Reproduce the new synthetic exercise and regressions

Use Python 3.13 and the existing source installation instructions. In the activated
environment, from the repository root:

```sh
python examples/strict_status.py
python -m pytest tests/test_execution_hardening.py tests/test_budget_persistence.py tests/test_strict_profile.py
```

The exercise is scripted FunctionModel, with real file/HTTP effects: it reads an
untrusted status note, proposes an extra field, receives a policy rejection, sends
one valid report and retires the session. It reports actual receiver counts and
completion; no neural attack-activation rate is inferred.

For the complete suite build trusted dashboard assets first, as in CONTRIBUTING.
Windows and Linux use separate dependency environments. New tests cover owned
loopback response/audit faults, batched duplicate proposals, actual child-process
exit/restart, concurrent budget claims, retained-state corruption/migration limits,
retirement/grant races, expiry, >1,000 completed SDK sessions and legacy/strict
configuration behavior. Historical corpora, evidence and grading remain unchanged.

No new Qwen, Docker or hostile Windows filesystem validation is established by
these tests. Existing Windows handle guarantees, mutable local audit storage,
unreliable task recovery, provider/logging channels and incomplete independent
auditing remain limitations. See [the threat model](threat-model.md).
